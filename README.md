# Интерактивное резюме геймдизайнера — отклик в ООО «ГеймТек»

**Живая версия: https://kerarty.github.io/cv-gametech/**

Сделал одностраничное резюме-лабораторию под вакансию «Гейм-дизайнер» в ГеймТек.
Вместо списка достижений — рабочие инструменты: тюнер лайвопс-события, таблица
контента с живыми формулами, калькулятор вероятностей и метод разбора результатов.
Всё считается прямо в браузере, всё можно потрогать руками.

Без фреймворков, без сборки, без зависимостей. Пять файлов, открывается двойным
кликом.

## Зачем

Рекрутер тратит на резюме сорок секунд. Убедить его, что я умею считать баланс,
за сорок секунд нельзя — зато можно дать тул, который это показывает: покрутить
параметры события и увидеть, как меняется кривая прогрессии, доля игроков,
которые добираются до цели, и цена премиум-окна в энергиях.

Тот же приём, что в [cv-lesta](https://kerarty.github.io/cv-lesta/) и
[cv-top-games](https://kerarty.github.io/cv-top-games/), только под задачи
liveops-событий, а не под боевой баланс.

Отдельно сделал блок «Чего у меня пока нет». Коммерческого liveops-опыта у меня
нет, и называть это прямо дешевле, чем выяснять на созвоне.

## Что умеет

- **Тюнер события** — длительность, бюджет очков, темп игрока, кривая сложности,
  затухание по дням, цель в процентах бюджета. Считает кривую прогрессии для трёх
  когорт (новичок, средний, активный) и даёт вердикт по пяти проверкам.
- **Таблица контента** — редактируемые ячейки, колонки «доля дня» и «Δ к плану»
  считаются формулами, наведение показывает саму формулу. Кнопка отдаёт TSV с
  формулами — вставил в Google Sheets, она пересчиталась сама.
- **A/B вариант** — две конфигурации события рядом, шесть метрик на сравнение и
  рекомендация, что ставить в прод.
- **Вероятности** — таблица дропа: P(хотя бы раз), ожидаемое количество, EV,
  маржа попытки и вероятность собрать полный набор.
- **Чек-лист приёмки** — «в конфиге так же, как в документе». Отметки сохраняются
  в браузере.
- **Разбор** — метод работы с цифрами и отзывами игроков: срез, вывод, одна гипотеза
  на следующую итерацию.
- **Разбор компании** — что я понял про Pines Peak, MMO-файтинг и midcore-экосистему
  и что конкретно приношу в каждую область.
- **Соответствие вакансии** — каждый пункт требований ссылается на раздел, где закрыт.

## Запуск

```bash
start index.html
```

Если нужен локальный сервер — для экспорта CSV и работы с буфером обмена:

```bash
python -m http.server 8777
# http://localhost:8777
```

## Технологии

- HTML, CSS, JavaScript — без фреймворков и без сборки
- Canvas 2D для графиков
- `localStorage` для чек-листа и черновика таблицы
- Шрифты системные, картинок и библиотек нет — страница весит меньше мегабайта

## Как устроено

```
index.html    разметка секций
styles.css    тёмная тема, адаптив, стили для печати
content.js    ← весь текст резюме здесь
balance.js    модель события и расчёты, чистая логика без DOM
lab.js        лаборатория: графики, таблицы, вкладки
main.js       сборка статичных секций из content.js
```

Правило одно: **любой текст и любая цифра меняются только в `content.js`.**
Остальные файлы данные оттуда не дублируют.

### Модель считает три независимые величины

Именно их разводит дизайнер, и именно поэтому тюнер что-то может исправить:

1. **Бюджет события** — сколько очков разложено на всё событие
2. **Темп игрока** — сколько он набирает в день, с затуханием: на четвёртый день
   остаются не все
3. **Кривая сложности** — как бюджет распределён по дням, отсюда «план»: сколько
   должно быть накоплено к концу дня N

Плюс **цель** — доля бюджета, без которой не открываются финальные награды.

Проверки вердикта:

| Проверка | Красная зона |
|---|---|
| Освоение бюджета средним | < 82% — не добирает; > 122% — награды не ценятся |
| Разрыв когорт | > 85 п.п. — активный улетает, новичок выпадает |
| Хвост события | > 60% аудитории не достигает цели |
| Премиум-стена | до цели не хватает больше полутора дней энергии |
| График | средний идёт в срок меньше половины дней |

Модель считает распределения по когортам, а не поштучный исход отдельного игрока.
Для решения «должно ли событие закрываться» этого хватает; для прогноза конкретного
процента конверсии нужны данные аналитики проекта.

## Что смотреть в первую очередь

Скриншоты не приложил: окно браузера ушло в фон, снять не вышло. Если что-то
внутри и правда не открывается — опишите, поправлю.

По порядку, если смотреть со второго экрана:

1. **Вкладка «Событие»** — главное. Потяните «Нарастание сложности» вправо и посмотрите,
   как зелёная линия набора уходит ниже золотой линии плана, а вердикты внизу
   перекрашиваются в красный. Это и есть баланс события, посчитанный, а не описанный.
2. **«Таблица контента»** — вбейте в первую строку `99999` в колонку «Очки».
   Колонка «Δ к плану» пересчитается, а наведение покажет формулу, по которой она считается.
3. **«Вероятности»** — увеличьте число попыток и посмотрите, как P(хотя бы один S-тир)
   растёт медленнее, чем ожидаемая ценность.
4. **Раздел «Чего у меня пока нет»** — прочитайте первым, если вы рекрутер. Там честно.

## Что доделать перед отправкой

- **PDF-версия.** Кнопка «В PDF» печатает страницу целиком со всеми вкладками.
  Нужен отдельный одностраничный A4: текст лежит в `content.js`, оформление — в
  блоке `@media print`. Ссылку на файл повесить в шапку.
- **Версия в ссылках.** `index.html` подключает скрипты как `?v=1.0`. GitHub Pages
  держит файлы в кэше около десяти минут: после правки поднять число в `index.html`
  **и** в последней строке `SIGN.changelog` в `content.js`.
- **Первый живой тираж.** Если до отклика появится боевой опыт — вписать его в
  раздел «Кейсы» и в `SLICES` в `lab.js`. Это самый сильный аргумент на этой вакансии.

## Планы

- Вторая вкладка тюнера — симуляция боя на тех же параметрах, чтобы когорты
  проверялись не только по кривой прогрессии
- Сохранение нескольких конфигураций события в `localStorage` и сравнение их между собой
- Выгрузка графиков в PNG — для вставки прямо в дизайн-документ
